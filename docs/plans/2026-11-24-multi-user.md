# 多人使用：人员、授权与多人群聊

- 日期：2026-11-24
- 相关：[浏览器远程客户端](2026-11-17-web-remote.md)、[移动端客户端 API](2026-10-24-mobile-api.md)、[群聊](2026-10-07-group-chat.md)、[角色与权限](2026-10-07-roles-and-permissions.md)、[消息账本](2026-11-10-message-ledger.md)、[MCP 访问](2026-11-20-mcp-access.md)

## 为什么

DS Bot 只有一个隐含的「用户」：坐在 DSH 网页或桌面应用前的那个人。手机 App、浏览器远程、IM、MCP 访问都只是这个用户说话的通道，现有通道按设备或渠道分配能力，未建立员工身份和按人的会话范围。群聊的成员只有 Bot。

公司内部的场景不是这样：主人希望员工只能用被授权的 Bot 和群，群聊里有几个人和几个 Bot 一起说话，谁说了什么要分得清。

取舍（2026-11-24 与主人定下）：

- **企业版用同一台服务器上的 Docker Compose 部署网页、员工 API 和运行 DS Bot 插件的 DSH。** 浏览器通过同源 HTTPS 访问员工 API。
- **员工使用独立的企业账号。** 管理员邀请员工并授权。员工可在多设备登录，调用身份由服务端登录会话解析。
- **企业版私聊按员工隔离并支持限量并发。** 每名员工和每个获授权的 Bot 之间有一条持续对话。管理员在控制台查阅全部员工对话。此项作为现有会话设计的企业版例外提交维护者评审。
- **主人授权，先不做 SSO 和管理员。** 主人在设置里建人员、勾范围、发邀请链接、撤销。
- **员工只能聊天。** 不能改 Bot、群、设置、权限预设、密钥。

## 第一版设计

### 人员

- 团队数据里多一张人员表 `state.people`：每个人 `{ id, name, color, botIds, createdAt, revokedAt? }`。`botIds` 是这个人可以私聊的 Bot。
- 主人不是人员表里的一行：主人就是在 DSH 网页、桌面应用或没绑定人员的设备上说话的人。行为和现在完全一样。
- 只有主人能增删改人员（设置里的端点，和其它设置一样只在电脑上可用；Bot 的工具里没有人员的参数，Main Bot 也不能给人授权）。
- 人员上限 200 人，名字最长 40 个字、不重复。隐私 Bot 不能授权给人员，也不出现在人员的可选列表里。

### 员工账号与邀请

- 管理员新建员工账号，设置可用 Bot 和群，生成短期一次性邀请。员工通过邀请激活本地账号，设置登录密码。服务端保存密码哈希和邀请凭证哈希。
- 网页与 API 同源。登录使用带 Secure、HttpOnly 和 SameSite 的 Cookie，写请求检查请求来源并实施 CSRF 防护。登录和邀请兑换限流。
- 员工更换设备时使用同一账号登录。管理员可撤销登录会话或禁用账号。禁用后所有登录会话和消息订阅失效，未执行任务重新检查授权。密码重设由管理员发起一次性重设邀请。

### 主机授权与会话边界

- 企业 API 从登录会话导出员工身份，通过内部调用上下文传给 DS Bot。处理器解析实际资源并在读取或执行前检查权限，身份字段由服务端提供。
- 员工 API 采用独立的业务操作白名单，默认拒绝未知操作。插件侧对私聊归属、群成员、附件和任务再次检查权限。订阅和重连沿用同一套会话范围。
- 允许的端点（聊天所需的全部）：
  - 读：`hello`、`state`、`notices`、`avatar`、`chat`、`room-chat`、`image`、`markdown-image`、`file-text`、`file-download`
  - 写：`send`、`stage-image`、`answer-question`、`view-reply`，以及能够定位到单条本人任务的停止操作
- 其余端点（建删改 Bot 和群、设置、记忆、密钥、连接器、IM、用量、定时任务、浏览器接管、MCP 访问、账号管理、以后新增的）回 `bot/refused`：「Not available for a team member. Ask the owner.」
- 范围检查：凡是请求里带 `sessionId` / `botId` / `roomId` 的端点，先解析到 Bot 或群，再看人员有没有权限：私聊同时检查 `person.botIds` 和会话所有者，群看 `room.people`。没权限回 `bot/refused`，不说目标存不存在。
- 提问卡和视图卡按服务端记录的发起人员与任务 ID 授权。超出 Bot 常规权限的调用进入下述规则裁定。多人消息合并后，无法确认归属的卡和任务只允许主人处理。员工停止操作不影响群里其他人触发的工作。
- `state` 对人员是一份投影：`bots` 只列可私聊的 Bot，并去掉指令、文件夹、任务、记忆统计，只留聊天界面要的字段（名字、角色、颜色、头像、会话段、等待 / 阻塞状态、最后一句）；`rooms` 只列它是成员的群；`sections` 随之过滤；`mainBotIds` 为空；`workspaceId`、`phone` 不给。`notices` 和 feed 的 `message` / `group` / `room` / `question` / `approval` / `done` 只推它看得到的会话。
- 每条员工消息照常让目标 Bot 按自己的权限预设跑一轮：共享 Bot 和群成员可执行的工具是员工实际可触达的权限。员工入口在工具和数据边界验证完成前保持关闭。共享配置默认禁用可接触主人工作区、密钥或未授权会话的工具。容器的完全权限配置不能作为员工执行环境。

### 员工规则与工具调用裁定

- 管理员为员工配置规则，指定适用的 Bot 或群、动作、资源范围和用途条件。第一版沿用主人控制台管理权限。
- 员工规则适用于其触发的工具调用。主机先检查身份、会话权限、动作、资源和明确禁止项。超出 Bot 常规权限且在管理员配置的可裁定范围内时，由独立 LLM 判断该请求是否满足用途条件。
- 裁定模型只接收当前规则、待审动作和必需的上下文。模型返回允许、拒绝或无法判断，并提供命中的规则及理由。主机校验输出，对当前请求、具体参数和规则版本执行单次许可。
- 缺少规则、调用归属不明、模型超时、输出无效或裁定期间撤权时，当前调用不执行。群聊按触发任务的原始成员身份裁定，接力保留该身份。平台硬性限制持续生效。
- 审计记录包含发起人、Bot、动作、规则版本、裁定及执行结果，敏感参数脱敏。首版覆盖管理员指定业务目录内的普通文件读取、创建和修改，读、写分别授权。每次写入绑定到具体目标和待写内容，支持在执行前检测目标版本变化。
- 执行器以管理员配置的业务目录为边界，在实际打开或提交文件时验证目标仍位于目录内。默认拒绝目录外目标、符号链接、硬链接、设备文件和版本冲突。员工工具配置仅开放能保证同等边界的结构化动作。文件删除、移动、任意命令和连接器不属于首批自动审批动作。
- `approval/request` 是现有单次审批接入点。验证 `tools/execute` 能否对普通执行与审批后的执行统一复查调用归属、实际参数和规则版本。对无法通过公开插件 API 拦截、归属或精确描述的动作，默认拒绝自动裁定。

### 署名：谁说的话

- 员工发言的 `by`（人员 id）和 `via` 由企业 API 经内部上下文传递。`channel.js` 的 `send` 把 `by` 交给 `rt.sendUser`，和 IM 的 `via` 一样进入消息的 `source`。
- 账本的群消息行、私聊的聊天条目（`parts.js` 里带 `via` 的那几处）、`room-chat` 的 `kind: 'user'` 条目都多带 `by` 和 `name`。
- 团队里有人员时，员工的消息进模型前在正文开头加一行 `[Message from <名字> via DS Bot web]`（和 MCP 访问的标明来源同一写法），主人的消息不加。标记只是信息，不是授权依据。
- 界面：群里和私聊里人说的每一句带名字和颜色；自己的消息仍靠右。主人控制台里 Bot 私聊当前这一段的用户消息由 DSH 画，暂时显示不了名字（和 IM 的「来自 …」同一个已知限制）。

### 员工私聊与限量并发

- 主机用人员 ID 与 Bot ID 定位员工私聊，首次发言创建会话。上下文换段后归属保持一致。多个获授权设备登录同一身份时继续同一条对话。既有私聊归原管理员。
- 聊天历史、上下文、附件、私聊学习所得记忆和任务都按会话归属隔离，跨段和异步回调沿用原归属。Bot 可共享管理员配置、模型和明确授权的业务资源。
- 同一会话的消息顺序处理。不同员工的会话占用独立执行配额，主机同时限制单 Bot 和总体活跃轮次。到达限制时等待空位，同一员工提交多条消息时保留消息顺序，重连按请求 ID 恢复状态。
- 管理员按员工或 Bot 查看员工私聊历史和附件，查阅入口只读，记录管理员、会话和查阅时间。员工首次私聊前看到管理员可以查阅的提示。
- 并发写同一业务文件时，提交仍须原子检查已审批的文件版本。一份更新成功后，基于同一旧版本的后续写入返回冲突。
- 实施前在隔离测试环境用 DSH 公开插件 API 验证两个独立会话可同时运行、停止一条会话不会干扰另一条，以及换段和重启能保持归属。
- 本地 mock 探测通过。暂停第一个 DSH 会话的模型响应后，第二个独立会话仍进入模型执行。企业版队列、停止隔离、换段和重启归属需要集成测试。


### 多人群聊

- 群多一个字段 `room.people`（人员 id 列表），和 `room.members`（Bot）并列。主人在群详情里加人、移出人；网页客户端只显示名单。
- 群里员工的发言就是一条用户消息。远端 Bot 的群第一版只做首轮流发言：沿用现有的 `@` 和管理员优先规则选出首批 Bot，并行派发，每次派发保留原始发起人。Bot 正在回答时的中途插话、进度触发的 `@`、接力与批次收回暂不启用，界面在员工发言时提示「进行中的轮次暂不接收新消息」。本地 Bot 所在群沿用原有规则。
- `@` 菜单在 Bot 之后列出群里的人；`@某个人` 只渲染成高亮的提及，不开轮、不叫人。
- Bot 的 `list_groups`、`read_group_chat`、群成员提示里带人的名字，让 Bot 知道群里有谁、谁在说话。`update_group` 没有人员参数。
- 每个群的人数的上限 100。员工不能建群、删群、改群设置。

### 企业网页客户端

- `hello` 多回 `who: { role: 'owner' | 'member', person?: { id, name, color } }`。员工登录后顶栏显示自己的名字。
- 员工看不到管理界面：设置里只剩「关于」和退出登录；新建 Bot、新建群、Bot 设置、群设置、记忆、用量、人员相关入口都不显示（主机本来也会拒绝，这里是别让人点了才知道）。
- 聊天里别人的消息带名字和颜色；`@` 菜单列人；群详情显示人。
- 「需要你处理」只列员工自己能答的卡（主机已过滤）。

### 部署到同一台服务器

- 由 Compose 启动公开的 HTTPS 入口、企业 Web/API 服务和内部 DSH 服务。网页与企业 API 使用同一个域名，消息实时推送走同源 SSE。
- DSH 与 DS Bot 插件在内部网络运行。现有 DSH 管理界面通过管理员专用网络或 SSH 隧道访问。企业 Compose 的员工入口仅发布网页与员工 API，DSH 管理端口和插件内部桥接端口均不公开。
- Web/API 服务通过内部身份认证调用 DS Bot 插件的专用业务适配层。适配层复用 DS Bot 的会话、排队与工具裁定逻辑，暴露指定业务操作。先验证适配层可基于公开插件 API 挂接，验证通过后再接员工网页。
- 持久化账号与登录状态、授权规则、对话、审计和业务文件。Compose 重启后恢复员工权限与私聊归属，并验证备份可恢复。
- 已有手机远程和浏览器配对属于独立入口。企业 Compose 可在未配置 Relay 的环境启动和验收。

### 远程 DSH 执行节点

- 管理员在各目标服务器的 DSH 安装执行节点插件，登记节点的内网 HTTPS 地址、身份和允许使用的工作区与 Agent 预设。每个远程 Bot 绑定一个节点和一套工作区、预设配置。企业后端与节点进行双向身份校验，浏览器只连接企业 API。
- 企业后端持有 Bot、员工、群和会话归属。节点用插件公开接口创建专用 DSH 会话，返回进度、回复和执行状态。员工私聊按人员与 Bot 隔离，群会话按群与 Bot 隔离。节点只返回本次获授权会话的事件，企业后端按会话归属同步记录供员工使用及管理员查阅。现有远端会话与历史继续留在原节点。
- 中心负责员工规则和 LLM 裁定，节点负责实际执行。节点将权限限制在本机明确配置的业务目录内，在提交前校验人员、会话、动作、目标、内容、文件版本和有效授权。中心失联或无法确认授权仍生效时，节点拒绝新的文件动作。节点环境仅开放符合目录规则的结构化文件工具。
- 中心在同一个持久化事务中处理提交许可与撤权。管理员发起撤权后，中心立即停止签发该授权下的新许可。此前已登记的许可可能完成，界面显示「撤权处理中」。所有在途操作均已确认完成、取消或确保无法再提交后，撤权才完成。节点断线、超时或重启时，待确认的许可仍然阻止撤权进入完成状态。重复请求只能查询原许可状态。
- 每个请求携带稳定 ID，节点保留执行回执，企业后端按事件序号恢复更新。节点断线时界面区分离线与结果待确认。连接恢复后先查原请求状态，结果无法确认时保留待确认状态。已经提交的文件修改依靠审计回执核对。
- 首版允许本地 Bot 和远端 Bot 一起入群。单 Bot、单节点与全局分别限并发。节点运行时用模拟模型验证创建会话、独立并发、流式回包及取消，再验证跨节点权限、回执恢复和管理员查阅。部署基于 DSH 公开插件 API。

## 不做什么

- 不接 SSO / OIDC / LDAP，不做人员管理员。
- 员工与 Bot 的私聊固定为每人每 Bot 一条。
- 不让 Bot 给人授权、拉人进群、移出群。
- 不做 DSH 网页的多用户登录；员工不走 DSH 网页界面。
- 第一版不把 IM 账号绑定到人员（人员表和署名的设计留了这条路：IM 的 `paired` 条目以后可以带 `person`）。
- 员工不看用量、记忆、设置、文件面板、浏览器画面；不做已读。

## 已知限制

- 员工的消息让 Bot 按自己的预设跑一轮：预设放行的操作不需要审批，员工就能让 Bot 做。授权前先看预设。
- 企业私聊的并发上限由主机配置。达到上限时，请求进入有界队列，员工网页显示排队和执行状态。
- 主人控制台里 Bot 私聊当前这一段的用户消息显示不了名字。
- 设备就是身份：员工换浏览器、清站点数据都要重新邀请；两个人的浏览器如果共用一个站点数据，就是同一个人。

## 实施和验收

1. 主机核心。设备邀请、授权与撤销、署名及资源检查。验证公开审批接口后，加入规则版本、LLM 单次裁定与审计。使用 mock 模型覆盖规则命中、明确禁止、模型输出异常、多人群归属不明和等待期间撤权，并验证这些用例是否实际执行了工具。目录读写验收覆盖正常读、创建和修改、读写权限分离、目录外目标、链接、裁定后目标变化、待写内容变化、文件版本冲突和失败后内容完整。测试未授权的历史、附件、通知、流式事件和内嵌状态均不返回。移除成员时断开或重置其订阅，并重新检查尚未开始的请求。
2. 主人控制台。提供人员管理、Bot 授权、群成员管理、员工权限规则编辑与裁定记录。提供只读的员工私聊查阅入口，支持按员工或 Bot 筛选并审计查阅。首次共享既有群聊前展示历史可见范围，由主人明确确认。
3. 员工网页。显示已授权的会话与署名。用主人、员工甲、员工乙三个独立浏览器上下文验收，覆盖同时发言、禁止访问另一群、卡片归属和撤销后重连。群授权只开放该群，群里的 Bot 不因此开放私聊。
4. 自托管上线。只发布企业 HTTPS 网页和员工 API。验证无 Relay 配置时能完成邀请、登录、聊天、流式回包和撤权，并验证员工网络无法访问 DSH 管理端口。先用测试团队试点，再授予真实员工权限。

5. 远端执行。用两台独立 DSH 测试实例验证节点身份、私聊与群聊归属、目录规则生效、节点掉线恢复，以及撤权后文件保持原样。

### 主机端交付顺序

| 任务 | 范围 | 交付证据 |
|---|---|---|
| 执行接口验证 | 在 `dev` 上使用 DSH 公开插件 API 验证 `approval/request` 与 `tools/execute` 的顺序及调用参数 | 使用临时业务目录与 mock 模型，展示同一调用获准后执行一次，拒绝后原文件不变 |
| 员工与会话授权 | 员工账号和登录会话、独立私聊归属与调度、多人成员名单、原始请求归属 | 两名员工均能在授权群发言，并能同时向同一个 Bot 私聊。管理员能查阅两条对话。跨员工读取历史、附件、记忆或事件被拒绝。达到上限时排队，撤权取消排队并停止后续未执行动作 |
| 业务目录工具及裁定 | 普通文件读、创建、修改，规则版本、调用级许可和脱敏审计 | 核对读写分权、路径约束、文件版本冲突和混合来源。留存实际文件变化与审计证据 |
| 界面与部署 | 管理员规则编辑、员工网页和 Docker Compose | 用管理员与两名员工的独立浏览器完成邀请、同群发言、读写裁定及撤权验收 |

在 `origin/dev` 已定位到审批和执行事件。员工网页按企业 API 设计，主机端执行接口和内部适配层的验证可从 `dev` 开始。

本地 DSH 0.2.2-rc.1 mock 工具探测已确认 `tools/execute` 能读取调用 ID 和结构化参数，并在工具开始前阻止对照调用。探测未覆盖 `approval/request` 到真实文件提交的完整链路，员工归属与撤权仍需联调。
